01
Public-Safety Command Platform

Incident-Event Pipeline

3systems on one stream
0producer changes per new consumer
Problem
The command, support and field systems all needed the same incident events. Point-to-point calls coupled them tightly, so a slow or failed system held up the others.
My part
Designed the gRPC-to-Kafka flow: the gateway contract, the incident topics and one consumer group per downstream system.
Key decisions
Typed gRPC contracts at the edge · a separate consumer group per system to isolate failures · producers never know who consumes their events · raw events are logged for later checks.
Result
Systems scale and fail independently, and new consumers attach without changes to producers.
What I learned
Decoupling starts with the contract, not the broker. Once the event shape was typed and stable, adding a consumer became a low-risk change.

Organisation-Tree Query Tuning

120s → 0.4suser loading time
~300×faster, no new infra
Problem
Loading the users of an organisation and its sub-units took about two minutes, which made the screen unusable for daily operations. It surfaced during a re-platform from .NET to Spring Boot that migrated 1M+ records with live sync.
My part
Traced the execution plans, found the costly filter and shipped the query fix.
Key decisions
Fix the query before adding caching or hardware · filter on the indexed organisation ID instead of a hard-coded code · keep the query results unchanged.
Result
Load time fell from ~120s to ~0.4s, without new infrastructure or caching.
What I learned
Measure before changing anything. The execution plan, not intuition, pointed to one filter that looked harmless.

03
Enterprise Notification Platform

OTP Login & Access Policies

0redeploys to tune OTP rules
1access policy shared by every service
Problem
OTP codes needed protection at rest and against brute force, and administrators needed to tune the rules without a redeploy.
My part
Built the OTP flow (encryption, expiry, lockout, resend quota) and the per-group access-time and session-timeout policies.
Key decisions
Codes stored AES-GCM-encrypted · limits editable at runtime through an admin API · policies set per role group and pushed to other services over gRPC · debug mode guarded by config outside production.
Result
Login security rules can be adjusted per group at runtime, and every service applies the same access policy.
What I learned
Security rules change more often than code. Making them configurable mattered as much as the encryption itself.

04
Enterprise Notification Platform

Backup & Restore Engine

Backup and restore across Oracle, Elasticsearch and MinIO, split into Kafka batch jobs with Redis locking, encrypted archives and retries.

KafkaRedisMinIO
Read the case study
Problem

Backups covered large volumes of data in several stores, had to run safely with multiple pods, and restores were producing duplicate recipients.

Solution

A job takes a Redis lock (setIfAbsent with a TTL) so only one run proceeds. Work is split into batches published to Kafka, and a Redis counter tracks finished batches to trigger finalisation. Archive files are encrypted with AES-GCM before they reach MinIO.

Key decisions

The lock TTL keeps a crashed pod from blocking later runs · transient failures are retried with exponential backoff · the restore path was fixed so recipients are not inserted twice.

Impact

Backups run safely across pods, archives are encrypted at rest, and restores no longer create duplicate recipients.

05
Public-Safety Command Platform

Multi-Level RBAC & Incident Operations

Multi-level RBAC with data scoping by organisation tier, plus the fire-incident lifecycle and GPS-based resource dispatch.

RBACSpring SecurityOracle
Read the case study
Problem

Permissions differed at each organisational level, and a user should only see data from their own unit and the units below it. When an organisation changed tier, its role mappings had to follow.

Solution

A layered permission model (permissions → groups → roles) with data scoping by organisation, plus a migration that remaps roles when the hierarchy changes.

Key decisions

Scope is applied in the query instead of filtering results afterwards · permission groups keep the number of roles small · integration accounts get their own provisioning flow.

Impact

One permission model covers every account type, and access rules are kept in one place.
